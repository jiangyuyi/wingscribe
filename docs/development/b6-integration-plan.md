# B6 正式选片流程接入计划

2026-10-21：用户要求回到主线，按可独立验证的小批次继续。B5 的离线算法与三模式已可用，但准确率未校准；本阶段不以校准完成为前提冒充可靠失焦判断。

1. **B6a（本批）：存储边界。** 同一本地 SQLite 中新增独立选片表和迁移版本，依赖 B4 原片版本。保存不可变分析报告及明确版本映射、人工 keep/undecided/reject 和备注、全局默认模式及分析组覆盖。默认 safe；组覆盖可删除以恢复跟随。人工标记绑定文件版本，不自动继承到被替换的新照片。重算只增加快照，不覆盖人工决定。已有数据库先备份，迁移事务化、可重复；不触碰真实用户数据库。
2. **B6b：应用服务与任务。** 原片扫描/登记 → 只读 JPEG 分析 → 候选分组/模式结果 → 原子保存快照。持久任务进度、失败、取消、恢复；禁止沿用归档裁切图作选片输入。建立缓存键与模型/算法/参数版本关系，结果绑定完整文件哈希。
3. **B6c：Web 接入。** 新选片入口、任务状态、并排比较、三模式和全局默认设置、人工决定保存。统一使用 B6a 仓储和 B6b 服务；模式变化不改人工标签。浏览器验收和隔离真实 JPEG 验证。
4. **B6d：人工调整。** 分组合并/拆分、主体切换，保留来源、历史和重算影响；不让旧建议覆盖人工结果。
5. **B6e：可恢复隔离。** 用户已确认同来源内隔离、执行前预览；按 [B6e 计划](b6e-quarantine-plan.md) 完成服务及页面。reject 本身仍只是标记，单独确认隔离才移动；不永久删除，不自动处理归档副本。
6. **B7：发布收口。** 更新锁定安装器、迁移/备份说明、CPU/GPU 干净环境与 NAS 实机验收。云端在线验证继续跳过并标记。

B6a 验收：已有库迁移备份可读且旧记录不变；重复快照幂等、冲突拒绝；未知文件版本及哈希不匹配拒绝；整批失败回滚；重算后人工标签不变；新文件版本不继承旧判断；模式覆盖优先级与重启后持久化；不执行文件删除或照片改写。

## B6b-1 完成记录与使用入口

`src/application/culling.py:CullingService` 和 `scripts/run_culling.py` 已实现上述同步路径。逐张处理，不保留整批像素；目录/相机边界参与分组。Python 3.11 下通过 Windows reparse 属性排除 junction，不依赖 3.12 才有的 `Path.is_junction`。文件处理前后 SHA-256 校验，发生变化的输入不进入成功快照。

CLI 示例（参数中的路径必须换成实际选择的本地库、备份目录和照片来源）：

```powershell
.venv-gpu/Scripts/python.exe scripts/run_culling.py --source <照片目录> --db <本地SQLite路径> --backup-dir <迁移备份目录> --model installer/models/yolo26n.pt --device 0 --gap 5 --span 30
```

5 秒/30 秒只是实验参数，接口要求显式指定，未宣布生产默认。CLI 会显式初始化/备份所指定的库，不能随意指向正式库试验；应用服务本身要求提前初始化仓储。只支持已有本地模型，固定类别 14、阈值 0.5、尺寸 640，并记录模型 SHA-256。Ctrl+C 请求在文件边界停止；未提供强制终止 GPU 推理。CLI 输出 job_id、snapshot_id、完成数与失败明细，非 completed 返回码 2。

快照 run_key 为 `culling:<job_id>`，包含 job_id、输入完整性和错误清单；任务表是最终任务状态依据。快照发布与任务终态不是一个跨模块事务：若发布后进程退出，下次恢复仍标 interrupted，可保留此前发布的快照；不能仅凭有快照认定任务成功。目录遍历/库写入等全局异常中止任务并记 failed，不发布可能被误认为完整的报告。单张读入失败没有可信文件版本时仅记原片观察；不伪造版本任务项。

## B6b-2 缓存实施契约

缓存按原片版本 + 完整 SHA-256 + 检测器身份/参数 + 评分算法/参数 + 输入协议及相关运行库版本定位。采用保守版本隔离，同内容的新文件版本也不自动共用。分组时间参数和建议模式不进入逐图缓存键，每次重新分组并计算三模式；人工决定独立保存。缓存仅包含检测框和评分证据，路径、拍摄元数据重新读取，不沿用旧报告位置。

每次仍读 JPEG 并核验完整哈希，命中只免检测和评分，不承诺免 NAS 读取/解码。成功分析（包括无主体/无法评分）且分析后哈希通过后先原子保存缓存，再完成任务项和发布报告；推理/读取失败不缓存。中断后以新请求重扫，复用已落盘条目，旧任务历史不改写。缓存损坏按未命中重算并修复，不能悄悄用损坏证据。新增 schema v2，旧库备份后迁移；用户正式库本批不迁移。

验证：命中零检测调用、文件/模型/评分变化失效、分组变化可重用、取消与发布失败后恢复、无框结果可复用、坏缓存重算、v1 迁移保留人工标记。真实 GPU 使用隔离 12 张副本两次运行，核验第二次缓存命中、输出一致与源哈希不变。

## B6d-1 分组修订存储与接口契约

本批先完成可独立验证的后端修订接口，下一批 B6d-2 接入页面操作与浏览器验收，主体切换另做 B6d-3。分组调整只复用保存的逐图证据重排建议，不读取照片、不调用模型、不修改缓存或人工决定。

- 拆分：指定一个组及其中非空、非全集的照片集合，生成所选/其余两组；各组内保留原顺序。
- 合并：指定同一快照内至少两个不同组，按原报告组及成员顺序合并；人工操作可覆盖自动时间/目录边界，三模式的尺度与质量保护仍有效。

- 未变组继承显式模式；拆出的组继承原组显式模式；合并组仅在所有来源组显式覆盖完全相同时继承，否则跟随全局默认。全局默认不固化为覆盖。
- 快照与组模式复制同一事务提交；客户端 request_key 幂等，同键不同操作拒绝。对旧修订继续调整会形成分支，不覆盖另一分支；历史接口提供父子关系，后续界面须明确当前版本。
- HTTP 只接收操作、组 ID、照片 ID 和请求键，不接收评分证据/任意报告；复用同源写入保护。未知、重复、空集合及全部拆出均拒绝。

验收覆盖拆分/合并重排、全部成员唯一保留、模式继承及冲突、原报告与人工标签不变、重试幂等、非法输入无写入、事务故障回滚、重启后历史读取。使用隔离数据库，不迁移正式库，不涉及文件隔离或删除。
