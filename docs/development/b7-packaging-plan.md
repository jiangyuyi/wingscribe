# B7 安装器依赖与发布收口计划

初稿：2026-10-22。独立推进构建准备，不发布新版本、不改用户安装目录。B6e 已按用户确认完成同来源可恢复隔离及执行前预览；当前进入 B7c 安装器验收，B7d VirtualBox 已安装且硬件配置完成，客体 Windows 尚待安装。各节初始问题和阶段结果按时间保留，最新结论见 [项目状态](status.md)。

## 发现与分批实施

当前 build.ps1 CPU 使用 torch 2.4.1/torchvision 0.19.1，GPU 2.10.0/0.25.0；手工 requirements 与 uv.lock 不一致，且构建直接复制开发 config（可能包含个人路径或密钥）。现有自检仅导入模型/静态文件，不能证明依赖或首次配置可用。

1. B7a：从唯一 uv.lock 离线导出 CPU/cu128 带哈希运行依赖；记录锁和导出清单哈希，提供过期检查及缓存 wheel 校验。先交付和验证导出工具，不立即执行旧构建。
2. B7b：构建消费这些清单并启用哈希/变体校验；默认可信国内镜像直连，保留官方下载回退说明，禁止下载失败后假报成功。清理仅限已验证的构建目录。源码/文档及配置白名单打包，排除个人配置和密钥；已有缓存构建必须自检版本。
3. B7c：隔离 CPU/GPU 安装暂存验证、升级/迁移备份、无配置首次启动、离线模型/选片闭环；不将开发环境通过当作安装包通过。
4. B7d：干净 Windows 与真实 NAS 故障、安装/卸载及发行产物哈希记录。缺少可用验收环境时如实标记，云端线上继续跳过。正式发布需最终确认版本与渠道。

B7a 验收：CPU/cu128 导出确定性、每项精确锁定带哈希、不包含 dev、PyTorch 变体一致；清单或 uv.lock 改动检测失败；本地 wheel 哈希必须属于锁文件，损坏即失败。导出过程离线且不更新 uv.lock，不触发包下载。

### B7a 使用

`python scripts/export_installer_lock.py --uv <uv可执行文件>` 离线生成两种依赖清单及 manifest；`--check` 检查导出是否与源码锁一致；`--wheel <wheel路径>` 校验缓存文件名与完整 SHA-256 是否匹配锁文件。更新 pyproject.toml/uv.lock 后必须重新导出并审查差异。

B7a 阶段曾未接入旧构建；现 B7b-1/2 已接入。完整安装包验收仍按 B7c/d 执行。

## B7b 分批执行顺序（2026-10-23）

1. B7b-1 先收口源码载荷：固定配置/运行脚本/参考数据白名单，清除构建缓存中的旧个人配置；每次清理前确认绝对路径和 reparse point 边界。带齐文档、AviList 和所选带哈希依赖，生成载荷 SHA-256 清单；独立暂存检查不启动旧构建、不修改用户配置。
2. B7b-2 接入锁定安装与缓存版本自检：统一 CPU/cu128 版本，所有 wheel 完整校验，先下载后离线安装。可信国内镜像直连，明确失败回退，不读取系统 pip 配置或悄悄沿用代理。
3. B7b-3 审查 Python/ExifTool 下载及运行时优化、Inno 升级/卸载边界，完成后才运行 B7c 完整隔离构建；不能将载荷检查当作安装包成功。

PyTorch 镜像参考：[南京大学镜像说明](https://help.mirrors.nju.edu.cn/pytorch/) 及 [SJTU 镜像说明](https://mirror.sjtu.edu.cn/docs/pytorch-wheels)。版本是否可用以实际下载及 uv.lock 哈希为准，不改版本迁就镜像。


### B7b-3 边界收口顺序

- 先移除新安装器的递归卸载删除规则，保留应用运行后产生的配置、数据库、备份和照片；取消依赖安装后的裁剪，保持 wheel 安装内容完整。ExifTool 缺失或无法执行必须阻止构建成功。
- 旧版 Inno 默认追加卸载日志，删除新脚本中的规则并不能证明旧版升级后的卸载安全；升级迁移需独立验证旧日志影响，未完成前不能宣称支持覆盖旧安装目录。不会自动运行旧卸载器或删改其日志。
- 随后固定 Python、pip 引导、ExifTool 的下载版本与可信哈希，审查缓存及解压边界；完整构建必须等这些检查完成。当前旧 Python 下载仍为 3.11.8，不能将开发解释器 3.11.17 当成安装运行时已升级。
- B7c 用全新独立目录验收首次启动和 CPU/GPU 运行，再做有配置/数据库的升级和卸载实验；正式安装目录及照片不参与实验。

依据：[Inno 卸载删除规则](https://jrsoftware.org/ishelp/topic_uninstalldeletesection.htm)、[卸载日志追加行为](https://jrsoftware.org/ishelp/topic_setup_uninstalllogmode.htm)。


### B7b-3b 运行时固定与安全解压（2026-10-23）

- Python 保持既有 3.11.8 embeddable，SHA-256 取自 python.org 对应发布的 Sigstore messageDigest；这不是声称完成 Sigstore 签名链验证，也不是升级到开发环境 3.11.17。后续替换运行时需独立评估并验证。
- pip 固定 25.0.1 wheel，哈希来自 PyPI 发布 JSON；直接离线解压引导，移除浮动 get-pip.py。二者首次实际下载均走华为镜像直连，官方哈希一致；支持 Range 续传、忽略 Range 时重下、完整哈希才接受缓存。
- ExifTool 使用仓库已跟踪的 13.40 ZIP，固定仓库归档 SHA-256（不是上游校验值），取消失效的 13.26 下载与系统任意版本回退；解压到各变体 build/tools，逐文件复验缓存并执行版本检查。上游归档来源链仍待发布前补证。
- 所有 ZIP 写入前检查 Windows 路径、越界、设备名、ADS、大小写重复、文件/目录冲突和链接；复用构建路径 reparse point 防护。_pth 无 BOM；不再从本机 System32 覆盖固定运行时 DLL。
- CPU/GPU 的 Python、pip、ExifTool 均已独立运行验证；依赖安装、整包启动、升级与卸载仍属于 B7c/d。旧安装日志风险仍然保留，不能对正式安装目录做覆盖验收。

来源：[Python 3.11.8](https://www.python.org/downloads/release/python-3118/)、[Python 归档摘要](https://www.python.org/ftp/python/3.11.8/python-3.11.8-embed-amd64.zip.sigstore)、[pip 25.0.1 元数据](https://pypi.org/pypi/pip/25.0.1/json)。


## B7c 隔离验收执行顺序

1. B7c-1：在 build-cpu/build-gpu 的独立解释器安装带哈希清单（全程离线）；验证全量版本、pip check、torch 变体及 FastAPI/OpenCLIP/Ultralytics 导入。记录 GPU 是否真的可用，不能把 CPU 导入等同 CUDA 推理。
2. B7c-2：重新暂存无个人配置的源码，启动独立端口、首次配置页面；只用独立数据库和已授权样本副本验证识别/选片/隔离恢复。避免使用正式 settings.yaml 和正式库。
3. B7c-3：编译安装器并在独立目录做新装测试；旧版升级/卸载另建含测试配置、数据库和照片的夹具，核实旧卸载日志影响及备份恢复。无法验证时保持阻止覆盖正式目录的发布门槛，不改用户安装状态。
4. B7d：干净 Windows、真实 NAS 故障以及正式发布信息仍独立保留，不以当前主机上的通过代替。


### B7c-3 分批检查（2026-10-24）

1. 固定打包 YOLO 文件与仓库指纹，不递归收集模型缓存；保留实验目录，不把 BioCLIP 下载残留收入载荷。恢复可用的固定 Inno 6.4.1 官方下载并验证签名。
2. 编译专用 ValidationBuild：独立 AppId、不写卸载注册项、不建快捷方式、不启动服务，产物仅供工作区隔离验收，不作为发布包。先 CPU，再 GPU。
3. 新装→放入测试配置/库/照片→同代升级→卸载，核对用户文件字节保留。旧式卸载日志未经迁移不得追加：缺少新一代标记时拒绝覆盖，保留旧目录，验证返回失败且不改文件。旧版自动迁移仍为后续门槛，不执行真实旧卸载器。
4. 编译成功后生成按变体/版本命名的产物 SHA-256 清单，覆盖 EXE 及实际存在的全部分卷；CI 同时保留清单。验证缺卷、空文件和下载后内容变更，清单不替代签名或编译成功检查。正式压缩 GPU 超限时再接入正式分卷与发布附件规则。
