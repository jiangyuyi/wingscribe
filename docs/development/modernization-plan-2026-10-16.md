# 工程现状评估与渐进改造计划

日期：2026-10-16。状态：方案草案，尚未开始业务改造。
实施更新（2026-10-25）：此文保留最初调查和方案，不是当前待办。AviList、原片登记/增量任务、JPEG 选片 Web 和可恢复隔离已分批实施，目前主线为 B7 安装器验收；当前状态及验收以 [项目状态](status.md) 和 [实施记录](execution-log.md) 为准。

已确认范围：个人 Windows 本地使用，照片可在 NAS；首版选片处理相机 JPEG，推荐清晰照片，疑似失焦照片提供预览、由用户决定是否删除；RAW 后续考虑。原图元数据写回开关本轮不处理。

配套：[工具链调研](../research/toolchain-review-2026-10-16.md)、[合焦选片方案](../research/focus-culling-plan.md)。

## 1. 结论

建议保留项目，进行有明确边界的核心流程重构，并将选片做成独立的分析能力。暂不进行全量重写。

问题集中在配置与初始化、流水线编排、任务状态、数据模型和接口接缝，不是 Python、FastAPI 或 SQLite 本身不适合。重写整个项目仍要重新解决 NAS 路径、分类数据映射、GPU 打包、人工标签迁移和 EXIF 编码问题；若缺少行为基线与统一契约，多 agent 交叉改动会再次产生同样的问题。

应当局部重写的是任务执行与结果记录，以及围绕“原始照片”的新选片数据模型。可以保留检测/识别模型适配器、路径解析经验、名录数据、评测工具和多数已有测试。

| 方案 | 收益 | 主要代价 | 判断 |
| --- | --- | --- | --- |
| 继续逐处补丁 | 短期改动少 | 选片继续依赖归档后裁切图，状态和配置分叉增多 | 不作为长期方案 |
| 全量重写 | 可一次调整结构 | 重做全部边界行为；没有可运行旧基线时难验证等价性 | 当前证据不足以支持 |
| 核心流程逐步替换 | 保留已验证能力，按阶段回滚，新选片不被旧流程束缚 | 需短期兼容适配与数据迁移 | 推荐 |

重新考虑全量重写的条件：完成可复现环境和一条新流程试点后，确认旧数据无法可靠映射、几乎所有保留模块均无法通过契约测试，或产品转向多人云服务。当前用户场景不具备这些前提。

## 2. 调查范围与验证边界

源码统计：59 个 Python 文件、10,813 行；43 个测试文件、7,954 行；三个页面模板共 2,438 行。行数只是定位依据，不代表质量评分。

重点检查流水线、检测/质量/裁切、识别基类与工厂、SQLite、Web 初始化和任务服务、配置读取、安装器及测试结构。102 个源码与测试 Python 文件通过 AST 语法解析。

未完成完整运行回归：仓库 `venv/Scripts/python.exe` 指向已不存在的 Python 3.11；当前系统 Python 3.12 缺少 pytest、Ultralytics、OpenCLIP 等必要依赖。没有覆盖或重装用户环境，没有下载模型和读取私人照片。旧文档的 `432 passed` 是历史结果，不能代表本次状态。

另执行了两个不加载模型、不访问用户照片的最小验证：路径前缀误判和质量分噪声反例。下文区分实测与静态风险。

## 3. 主要发现

| 问题与证据 | 状态 | 影响及处理方向 |
| --- | --- | --- |
| 根 `requirements.txt` 几乎没有版本约束；安装器另外固定 CPU torch 2.4.1、GPU 2.10.0；Python 下载固定 3.11.8 | 静态确认，旧 venv 失效已实测 | 无法方便复现已知可用组合；先建立依赖锁定与运行环境清单 |
| `src/web/app.py` 导入时读取并验证真实配置、建立目录 | 静态确认 | 没有合法配置时可能在设置页出现前就退出；改为应用工厂及独立首次配置流程 |
| `BirdRecognizer.predict*` 与 `AbstractBirdRecognizer.recognize` 并存，REST 工厂混用两类对象 | 静态确认 | 本地/懂鸟 REST 路径不能仅凭平台枚举认定可用；统一结果契约、隔离兼容适配器 |
| `SmartScanner.scan` 用字符串前缀排除目录；`LocalProvider._validate_path` 使用同类回退 | 最小验证复现 | 排除 `output` 时错误排除相邻 `output_backup`；访问边界也会接受该同前缀目录。用真实路径组件关系和多源根标识修正 |
| `process_image` 的临时文件仅由 `entry.name + detection_index` 命名 | 静态风险 | 不同日期目录的同名照片并发处理可能写同一临时文件；改为 job/asset/detection 唯一标识 |
| `run/run_by_folders` 等待 future，但不统一读取任务异常；最终状态主要只区分停止/完成 | 静态确认 | 完成日志不能证明每张照片处理成功；引入成功、跳过、失败计数和失败详情 |
| `inference_batch_size` 读取后未参与流水线分批；当前按单图内检测框调用识别 | 静态确认 | 调整配置不一定限制实际推理批次；统一有界队列和模型工作进程的批次策略 |
| `IOCManager` 1,055 行，混合 Excel 导入、查询、路径、统计和增列迁移 | 静态确认 | 新选片表继续塞入此类会加重耦合；分离照片仓储、分类仓储和版本化迁移 |
| `photos` 主要对应已归档检测裁切记录；未检出/被模糊过滤的原片可能没有记录 | 静态确认 | 不能用这张表直接列出所有失焦原片；必须先登记原片，再执行检测和分析 |
| 质量分在缩小、有 padding 的 JPEG 裁切上计算，混入检测分与鸟占比 | 源码与合成反例确认 | 不等于合焦程度；建立原始分辨率区域分析，并分开焦点、噪声、曝光和检测可靠度 |
| 约 7,954 行测试，但 `test_full_pipeline.py` 模块直接 skip，API 测试大量替换工厂/识别器 | 静态确认 | 单元测试是资产，但接缝仍可能失效；增加无模型权重的真实服务集成和少量模型冒烟 |
| GitHub 工作流包含打包与 Claude 操作，没有常规 PR pytest 门禁 | 静态确认 | 必须补自动回归，不能把构建导入自检等同于业务测试 |

此外，部分异常直接返回空列表，会混淆“没有鸟”和“识别失败”；任务日志是内存列表，执行线程还更改全局工作目录。应随任务执行重构解决，不再逐处添加状态变量。

## 4. 保留与调整的边界

保留：Python 推理生态、FastAPI、本地 Web 界面、SQLite、ExifTool、现有 BioCLIP2 基线、IOC 导入材料、独立评测与报告比较工具、经过审查的单元测试。

替换：散落配置读取、隐式默认值、Web 导入副作用、重复任务状态、无界/不明确的并发调度、按文件名生成临时路径、混合质量总分作为业务决策依据。

暂缓：MySQL、Redis/Celery、微服务、全站 React/Electron 重写、所有云平台统一上线、RAW、鸟眼模型训练和大模型美学打分。它们当前不能直接解决已确认问题。

旧云适配器先从主运行路径隔离；是否删除取决于实际使用情况，不把“个人本地使用”推断成允许删除所有云代码。

## 5. 目标结构

```text
Web / CLI
   -> 应用服务：导入、识别、选片、人工决策、归档
       -> 有类型的任务请求与结果
       -> 有界任务执行器（读取/解码、单模型工作进程、结果写入）
       -> 数据仓储（本地 SQLite）
       -> 外部适配器（照片目录、模型、ExifTool）
```

只按职责建立少量模块，例如 `application/`、`jobs/`、`storage/`、`culling/`、`adapters/`；不为了目录整齐一次搬动全部源码。旧 Web 路由作为兼容入口，逐项转调新应用服务。

核心实体：

- `Asset`：原片身份、source_id、相对路径、大小/时间/指纹、原始分辨率、拍摄时间和可用状态。
- `Detection`：归属 Asset 的鸟体框、可选头部/眼部区域和定位可靠度，一张照片可有多只鸟。
- `AnalysisRun/AnalysisResult`：分析版本、模型/参数/候选集标识、逐区域结果、失败原因和耗时。
- `CullingDecision`：人工保留/待定/拒绝与理由，不覆盖识别标签或自动分析。
- `Job/JobItem`：可持久化状态、错误与重试；崩溃后旧运行项标为 interrupted，可由用户续跑。

数据库与缓存留 Windows 本地；NAS 保存照片。以 `source_id + relative_path` 表示逻辑位置，盘符变化可重新绑定，不能将路径当作永久身份。

## 6. 分阶段实施与验收

| 阶段 | 交付内容 | 验收/退出条件 |
| --- | --- | --- |
| P0：复现基线 | 独立环境；依赖与模型清单；冻结已有功能清单；PR 测试工作流；最小测试图库 | 新环境可安装；记录真实 pytest 结果及失败归因；不使用用户 settings/数据库测试；至少一条 JPEG 全流程可复现 |
| P1：修正契约与基础错误 | 配置 schema/应用工厂；路径组件比较；唯一临时文件；识别适配层；真实失败状态 | 无配置可进入设置；同名前缀与多源测试通过；跨目录同名图无冲突；local REST 与流水线契约一致；出错不报告全成功 |
| P2：原片目录与新任务执行 | Asset/Detection/Analysis/Job 增量表；单模型工作进程；有界队列；数据库单写入边界；本地缓存 | 所有输入原片均有记录；无鸟、失焦、失败均可查询；NAS 断线不会误记删除；重复执行幂等；取消和崩溃可解释 |
| P3：JPEG 选片只读原型 | 元数据采集、候选分组、原分辨率鸟体评分、并排 100% 预览、人工选择；比较经典指标和 IQA | 先在冻结校准/测试组上验证；推荐与人工意见可追溯；无法判断单列；不自动移动/删除 |
| P4：可用的选片流程 | 相似组内 Top-K、失焦候选页、手动合并/拆组、保留标记、用户确认的隔离及恢复 | 多鸟与小鸟不过度自信；已保留图不会被后台重算推翻；NAS 失败有操作记录；恢复流程通过故障测试 |
| P5：收口与发布 | 逐步移除被替代入口；安装器使用锁定依赖；干净 Windows CPU/GPU 验收；导出与恢复说明 | 一个配置来源、一套分析契约；旧库迁移前后计数与人工标签一致；原片哈希不变；可回退旧版本 |
| P6：后续选择 | RAW 全链路、鸟头/眼模型、AviList 迁移、其他推理后端 | 每项有独立样本、性能/准确率门槛及数据迁移方案，再决定实施 |

P0 完成后，P1 的基础修复与 P3 的离线算法实验可独立推进；P3 产品界面依赖 P2。不要先把所有底层重构完才给用户看选片效果，也不要将试验评分直接接入删除。

每个阶段拆成可单独审核、测试、回滚的变更。环境锁定、行为修复、目录搬迁和模型升级分开提交，便于确定回归来源。

## 7. 数据迁移和回退

1. 在数据库副本上演练并保存迁移前结构、记录数、人工标签、路径清单；不先执行原地重建。
2. 新增表和迁移版本号，原 `photos.id` 保留，建立旧记录到 Asset/Detection 的映射。
3. 一张原图对应多个裁切，不能按裁切数量生成多个原片；绝对路径与旧相对路径统一解析后再归并，歧义记录隔离待确认。
4. 先让新选片只写新表，旧图库继续可用。逐条迁移读取入口，避免长期双写。
5. 版本切换期间不强制重识别全库；新结果按分析版本并存，人工确认优先保留。
6. 回退应用版本时保留旧表及原字段；若发生需要降级的不可逆 schema 变更，则从迁移前备份恢复，不承诺任意版本自动降级。

## 8. 多 agent 协作治理

导致混乱的不是 agent 数量本身，而是缺少共享契约、唯一状态源和集成验证。

- 新需求先写清输入、输出、不改变的行为、验收案例；不能只给出“优化识别”这类目标。
- 修改识别结果/配置/schema 先更新一个统一定义，不允许每个入口各造一个 dict 协议。
- 分工按模块边界，尽量避免同时修改流水线、数据库迁移和大型模板同一区域。
- 每个变更必须说明验证了什么、未验证什么；历史测试数量不作当前通过证据。
- 同一时间只推进一个主要架构迁移，不把模型升级、部署更换与新选片同时揉进一次提交。

## 9. 下一步需要讨论的产品参数

以下是 2026-10-16 的讨论清单。后续已确认自动分组、每组最多推荐 3 张、默认最大鸟体评分，允许按需选择推荐模式；已实现人工拆并、主体选择以及执行前预览的同来源可恢复隔离。尚未确定的 RAW、隔离长期清理策略和准确率泛化验证不因这些实现而自动完成。

已明确 JPEG、Windows/NAS、推荐清晰照片和人工确认删除。剩余参数不阻塞 P0/P1：

- 默认每组推荐 1 张还是 3 张，是否优先眼部清晰、如何对待翼部运动模糊。
- 自动分组只覆盖明显连拍，还是允许更宽松的相似场景；建议先保守分组并允许人工拆并。
- 多只鸟时由用户指定主体，或先采用默认主体并清楚标注。
- 隔离区保留多久、是否需同时清理衍生图；NAS 回收站能力必须实机核查。
- 实际显卡/显存、常见 JPEG 分辨率和单次照片量，用来确定性能验收预算。

本轮只交付分析与计划，没有实现新删除操作、修改照片或数据库，也没有改动原图写回策略。
